# Chatomatic — Project Memory & Decision Log

Living document. Updated as decisions are made, revised, or reversed. Most recent entries at the top of each section.

---

## Project Identity

**What it is:** A web chatbot replacing a traditional house-info website for a holiday home the owner lends to friends repeatedly. Guests ask questions; the bot answers from a Markdown knowledge base.

**Why it exists:** More interactive than a static site; the question log tells the owner what guests care about and what's missing from the guide.

**Current status:** Design spec complete (SPEC.md). Ready for implementation planning.

---

## Decisions Made

### 2026-05-13 — Full design session

| Decision | Choice | Rationale |
|---|---|---|
| Access control | Public (no login) | Trusted friends; login friction outweighs risk |
| Rate limiting | 30 req/IP/hour | Protects Claude API spend; owner chose this over URL token approach |
| AI model | Claude Haiku 4.5 (`claude-haiku-4-5-20251001`) | Document Q&A doesn't need Sonnet reasoning; 4x cheaper, faster |
| Prompt strategy | Prompt caching, full doc every request | Full accuracy + ~90% cost reduction after first request per cache window |
| API response | Non-streaming, structured JSON | Enables `{ answer, suggestions }` in one call; Haiku fast enough |
| Conversation context | Last 3 exchanges (6 messages) | Natural follow-ups without cost accumulation; not persisted across sessions |
| Suggested follow-ups | Up to 3 per response, generated by Claude | Rendered as green chips below bot answer; clicked = next question |
| Unanswerable questions | "I'm not sure — ask the owner" + log | Honest; no hallucination risk |
| Knowledge base format | Markdown with YAML frontmatter | Human-editable, no database needed, directly consumed by Claude |
| Frontmatter fields | `house_name`, `owner_contact`, `suggested_questions`, `arrival_brief` | All config in one place |
| Sensitive content | `[RESTRICTED]` heading tag | Owner marks sections; bot refuses to reveal content; system prompt enforced |
| Knowledge base updates | Edit `knowledge.md` directly, restart container | No admin UI; owner comfortable with files |
| Word doc ingestion | One-off `scripts/ingest.js` (mammoth + Claude API) | Converts existing .docx to structured knowledge.md; run once at setup |
| Knowledge gap analysis | `scripts/analyze-gaps.js` → `GAPS.md` | Cross-refs knowledge.md + questions.log; run before each knowledge base update |
| UI style | Bright & friendly — light gradient, rounded, holiday feel | Selected as option C from 3 visual options |
| Bot persona | Named after the house | Most personal; name set in frontmatter `house_name` |
| Starter prompts | 3–4 clickable chips, defined in frontmatter | Helps hesitant users; disappear after first message |
| "I've arrived" button | Amber button in header; one-tap; localStorage flag | Option B from 3 options; delivers arrival brief as bot message; button disappears permanently on device |
| Arrival brief delivery | Rendered directly from frontmatter, NOT via Claude | Ensures exact content shown as written; no model interpretation |
| Question log access | Daily email digest | Owner prefers passive delivery |
| Email sending | Nodemailer + Gmail SMTP app password | Owner has Gmail |
| Hosting | Docker on QNAP NAS via Container Station | Docker lighter than VM; Container Station is first-class on QTS |
| Reverse proxy / SSL | QNAP Application Portal + Let's Encrypt | Built into QTS |
| Network access | Internet-facing | Friends use it before arrival, not just on-site |
| Backend language | Node.js / Express | Single-process simplicity; no build step |

## Open Questions

- What is the house name? (Set in frontmatter `house_name` and/or `HOUSE_NAME` env var at deploy time)
- What email address for the digest? (Set via `DIGEST_EMAIL` env var)
- Digest time preference — default is 07:00; owner to confirm

---

## Things NOT to build

- Admin UI for editing knowledge base (owner edits files directly)
- Per-user login or accounts
- Public question feed ("what people are asking")
- RAG / vector retrieval (prompt caching + full doc is sufficient)
- Persistent cross-session conversation memory
- Streaming API responses (incompatible with structured JSON output)
- QR code / dedicated `/arrive` URL for arrival brief (owner chose header button instead)

---

## Constraints & Watch-outs

- `knowledge.md` must stay under ~15,000 tokens to stay within prompt cache efficiency range
- Gmail SMTP requires an App Password (not account password) — document clearly in setup
- QNAP Application Portal needs ports 80 and 443 forwarded from router for Let's Encrypt
- `[RESTRICTED]` is enforced by system prompt only — not cryptographic; don't store truly critical secrets without accepting this
- Docker volume path on QNAP varies by NAS model/setup — document with QTS-specific path examples
- `arrival_brief` items must be self-contained — they are rendered as a list, not parsed by Claude
- `GAPS.md` is generated output — add to `.gitignore`
