# Chatomatic — Full Design Specification

**Version:** 1.0  
**Date:** 2026-05-13  
**Status:** Approved — ready for implementation planning

---

## 1. Overview

Chatomatic is a web-based chatbot that replaces a traditional static website for a holiday home lent repeatedly to friends. Guests navigate to a URL and ask natural language questions about the property; the bot answers from a structured Markdown knowledge base maintained by the owner. The owner receives a daily email digest of all questions asked, including those the bot could not answer, to guide ongoing knowledge base improvements.

### Goals
- Simple, focused experience for guests — no accounts, no friction
- Owner can improve the knowledge base by editing a single Markdown file
- Owner gets passive insight into what guests care about and what's missing
- Runs reliably on a QNAP NAS with minimal ongoing maintenance

### Non-goals
- Admin UI for editing the knowledge base
- Per-user accounts or login
- Public question feed
- Vector search / RAG (prompt caching + full doc is sufficient)
- Persistent cross-session conversation memory

## 2. User-facing features

### 2.1 Chat interface

**Style:** Bright and airy — light gradient background (blue → green), white message bubbles, rounded corners, emoji accents. Friendly and holiday-appropriate.

**Layout (top to bottom):**
1. **Header** — house name, tagline ("Ask me anything about your stay"), "I've arrived" button (amber, see §2.4)
2. **Message area** — scrollable; starter chips on fresh session, message bubbles thereafter
3. **Input bar** — text input + send button; fixed to bottom

**Starter chips:** 3–4 clickable question chips shown before the first message is sent. Defined in `knowledge.md` frontmatter under `suggested_questions`. Disappear once conversation begins.

**Message bubbles:**
- User messages: right-aligned, blue background, white text
- Bot messages: left-aligned with small house avatar, white bubble, dark text

**Suggested follow-ups:** After each bot response, up to 3 contextual follow-up questions appear as green chips below the answer ("You might also want to know:"). Clicking a chip submits it as the next question. Generated by Claude in the same API call as the answer.

**Conversation context:** The last 3 user/assistant exchanges (6 messages) are included in each API call. Context is in-session only — not persisted to storage, not carried across page loads.

**No-answer response:** When the bot cannot answer from the knowledge base: *"I'm not sure about that — it's best to ask the owner directly."* The question is logged with `answered: false`.

**Restricted response:** When a question touches a `[RESTRICTED]` section: *"I can't share that here — contact the owner directly."* The question is logged with `answered: false, restricted: true`.

### 2.2 Knowledge base

The bot answers only from the knowledge base. It never invents or infers information not present in the document.

### 2.3 Rate limiting

30 requests per IP address per hour. Requests over the limit receive an HTTP 429 with a friendly message: *"You've sent a lot of questions — give it an hour and try again."*

### 2.4 "I've arrived" button

A prominent amber button in the header labelled "🏠 I've arrived". Visible on every session until tapped. When tapped:

1. The button is removed from the header immediately
2. A `localStorage` flag (`chatomatic_arrived`) is set — the button never appears again on this device
3. The bot sends a proactive welcome message containing the arrival brief (defined in `arrival_brief` in `knowledge.md` frontmatter)
4. The arrival brief is formatted as a friendly checklist: heating, keys, bins, Wi-Fi, owner contact

The arrival brief is not shown automatically — only when the guest deliberately taps the button. This avoids interrupting guests who open the chatbot before arrival for directions or pre-visit questions.

## 3. Knowledge base format

**File:** `data/knowledge.md`  
**Maintained by:** Owner — edited directly on the NAS, picked up on next container restart.

### 3.1 Structure

```markdown
---
house_name: Honeysuckle Cottage
owner_contact: owner@email.com
suggested_questions:
  - What's the Wi-Fi password?
  - Where should we park?
  - What time is checkout?
  - Any good restaurants nearby?
arrival_brief:
  - "🔑 Keys: leave on the kitchen hook when you go out"
  - "🌡️ Heating: thermostat in the hallway, default 20°C"
  - "🗑️ Bins: black bin Tuesday · recycling Friday · bags under sink"
  - "📶 Wi-Fi: CottageGuest / [password]"
  - "📞 Owner: [mobile number] if anything urgent"
---

## Wi-Fi
Network: CottageGuest  
Password: sunflower22

## Parking
Two spaces in the driveway. Please do not block the gate.

## Alarm Code [RESTRICTED]
The alarm code is 4821. Set it whenever leaving the property.

## Local Restaurants
The Fox & Hound is a 5-minute walk and serves food until 9pm...
```

### 3.2 `[RESTRICTED]` convention

Any Markdown heading containing the literal string `[RESTRICTED]` marks that section as sensitive. The bot is instructed via system prompt to:
- Acknowledge the topic exists if asked ("There is information about the alarm, but...")
- Never quote, summarise, or reveal any content under that heading
- Direct the guest to contact the owner

This is enforced by the system prompt, not by access control. Do not place truly critical secrets here unless comfortable that the enforcement relies on Claude's instruction-following.

### 3.3 Updating the knowledge base

1. Edit `data/knowledge.md` on the NAS (the file is in the Docker volume)
2. Restart the Docker container: Container Station → restart, or `docker compose restart`
3. The app reloads the file on startup — no rebuild required

## 4. Backend

### 4.1 Technology

- **Runtime:** Node.js 20 (Alpine in Docker)
- **Framework:** Express
- **Entry point:** `server.js`

### 4.2 Routes

| Method | Path | Description |
|---|---|---|
| `GET` | `/` | Serves `public/index.html` |
| `POST` | `/api/chat` | Rate-limited; calls Claude; logs question |
| `GET` | `/api/starters` | Returns `suggested_questions` and `house_name` from frontmatter |
| `GET` | `/health` | Returns `200 OK` — used by Docker health check |

### 4.3 `/api/chat` request/response

**Request body:**
```json
{
  "message": "What's the Wi-Fi password?",
  "history": [
    { "role": "user", "content": "Is there parking?" },
    { "role": "assistant", "content": "Yes, two spaces in the driveway." }
  ]
}
```
`history` contains at most the last 3 exchanges (6 messages). The client manages this.

**Response body:**
```json
{
  "answer": "The Wi-Fi network is CottageGuest, password sunflower22. 🌿",
  "suggestions": [
    "Is there a smart TV I can use?",
    "What time is checkout?",
    "How do I contact you if something goes wrong?"
  ]
}
```

### 4.4 Library modules

**`lib/knowledge.js`** — runs once at startup:
- Reads and parses `data/knowledge.md`
- Splits frontmatter from body
- Identifies `[RESTRICTED]` headings and their content boundaries
- Exposes: `getSystemPrompt()`, `getKnowledgeText()`, `getStarters()`, `getArrivalBrief()`

**`lib/chat.js`** — called per request:
- Builds Claude messages array: system (cached) + knowledge block (cached) + history + user message
- Sets `cache_control: { type: "ephemeral" }` on system prompt and knowledge block
- Calls `claude-haiku-4-5-20251001` (non-streaming, structured JSON response)
- Parses `{ answer, suggestions }` from response
- Returns result + `answered` + `touchedRestricted` flags

**`lib/logger.js`** — called per request after Claude responds:
- Appends one JSON line to `data/questions.log`
- Format: `{ "ts": "ISO8601", "q": "...", "answered": true|false, "restricted": true|false }`

**`lib/digest.js`** — scheduled via node-cron:
- Fires daily at time set in `DIGEST_CRON` env var (default: `0 7 * * *`)
- Reads `data/questions.log`, filters last 24 hours
- Groups into: unanswered, restricted-attempted, answered
- Sends plain-text email via nodemailer + Gmail SMTP
- Does not clear the log — log accumulates indefinitely

### 4.5 System prompt

```
You are [HOUSE_NAME] Assistant, a friendly and helpful guide for guests staying at [HOUSE_NAME].

Answer questions using ONLY the information in the knowledge base below. Do not invent, guess, or infer anything not explicitly stated.

If asked about a section marked [RESTRICTED], say: "I can't share that here — please contact the owner directly." Do not quote or summarise the content of restricted sections.

If you don't know the answer, say: "I'm not sure about that — it's best to ask the owner directly."

Always respond in a warm, concise, and friendly tone. Use the guest's question to generate up to 3 relevant follow-up questions they might want to ask next.

Respond ONLY as valid JSON in this exact format:
{
  "answer": "Your answer here.",
  "suggestions": ["Follow-up 1?", "Follow-up 2?", "Follow-up 3?"]
}
```

### 4.6 Prompt caching

Both the system prompt and the full knowledge base text are sent with `cache_control: { type: "ephemeral" }`. After the first request in each 5-minute cache window, subsequent requests pay ~90% less on those tokens. The knowledge base should be kept under 15,000 tokens to remain within the optimal cache range.

## 5. Frontend

**Technology:** Plain HTML, CSS, JavaScript — no framework, no build step.

**Files:**
- `public/index.html` — shell
- `public/style.css` — all styles
- `public/app.js` — all interactivity

### 5.1 Behaviour on load

1. Fetch `/api/starters` to get house name and suggested questions
2. Render header with house name + "I've arrived" button (unless `localStorage.chatomatic_arrived` is set)
3. Show starter chips in message area
4. Focus input

### 5.2 On message send

1. Append user bubble to message area
2. Remove starter chips (first message only)
3. Show typing indicator
4. POST to `/api/chat` with message and last 3 history turns (trimmed client-side)
5. On response: append bot bubble with answer, render suggestion chips below
6. Scroll to bottom
7. Update local history array (trim to last 3 exchanges)

### 5.3 "I've arrived" button

- Rendered in header if `localStorage.chatomatic_arrived` is not set
- On click:
  1. Set `localStorage.chatomatic_arrived = "1"`
  2. Remove button from DOM
  3. Render the `arrival_brief` array already loaded from `/api/starters` at page load — no second API call
  4. Render arrival brief as bot message (no API call to Claude — content is from frontmatter, rendered directly)

The arrival brief does not go through Claude — it is rendered directly from the `arrival_brief` array in the frontmatter to ensure it is always shown exactly as written, with no model interpretation.

### 5.4 Mobile

Fully responsive. Input bar fixed to bottom. Message area scrollable. Starter chips wrap gracefully on narrow screens.

## 6. Question log

**File:** `data/questions.log`  
**Format:** JSON lines (one object per line, newline-delimited)

```jsonl
{"ts":"2026-05-13T10:22:00Z","q":"What's the Wi-Fi password?","answered":true,"restricted":false}
{"ts":"2026-05-13T11:05:00Z","q":"What's the alarm code?","answered":false,"restricted":true}
{"ts":"2026-05-13T14:30:00Z","q":"Is there a kayak?","answered":false,"restricted":false}
```

**Retention:** Log accumulates indefinitely. No automatic pruning. The file is in the Docker volume and persists across container restarts and rebuilds.

**Interpretation:**
- `answered: true` — bot found and returned information from the knowledge base
- `answered: false, restricted: false` — bot didn't know; candidate for knowledge base addition
- `answered: false, restricted: true` — guest asked about a restricted topic; bot handled correctly

## 7. Email digest

**Schedule:** Daily at 07:00 server time (configurable via `DIGEST_CRON` env var)  
**Transport:** Nodemailer + Gmail SMTP (app password)  
**Format:** Plain text

```
[House Name] — Daily Question Digest — 13 May 2026

Questions today: 12  |  Answered: 9  |  Unanswered: 3

━━━ UNANSWERED — consider adding to knowledge.md ━━━
  14:30  Is there a kayak?
  16:12  Where's the nearest pharmacy?
  20:45  Can we have a bonfire?

━━━ RESTRICTED (correctly handled) ━━━
  11:05  What's the alarm code?

━━━ ALL QUESTIONS ━━━
  10:22  ✓  What's the Wi-Fi password?
  11:05  🔒  What's the alarm code?
  12:14  ✓  What time is checkout?
  ...

No action needed if all questions were answered.
```

If no questions were asked in the past 24 hours, no email is sent.

## 8. Scripts (one-off tools)

### 8.1 `scripts/ingest.js` — Word doc → knowledge.md

Run once during initial setup (and whenever you want to re-ingest a revised source document).

```bash
node scripts/ingest.js "House Guide.docx"
```

**What it does:**
1. Extracts plain text from the `.docx` using `mammoth`
2. Sends to Claude with a structuring prompt:
   - Organise content under clear Markdown headings by topic
   - Flag any content that appears sensitive (codes, financial terms, private contacts) with `[RESTRICTED]`
   - Extract 3–4 natural starter questions from the content
   - Write the YAML frontmatter block (`house_name`, `suggested_questions`, `arrival_brief` skeleton)
3. Writes the result to `data/knowledge.md`
4. Prints a summary: sections found, restricted sections flagged, token count estimate

**After running:** Review the output. Adjust `[RESTRICTED]` tags as needed. Fill in the `arrival_brief` items. Confirm `suggested_questions`. Then restart the container.

### 8.2 `scripts/analyze-gaps.js` — knowledge gap report

Run periodically (e.g. before updating the knowledge base between visits).

```bash
node scripts/analyze-gaps.js
```

**What it does:**
1. Reads `data/knowledge.md`
2. Reads `data/questions.log` if it exists
3. Sends both to Claude with an analysis prompt:
   - Surface unanswered questions from the log (highest priority)
   - Identify topic areas missing entirely from the knowledge base (common in holiday home guides)
   - Flag sections that exist but are thin or vague
4. Writes a `GAPS.md` report to the project root

**Example output (`GAPS.md`):**
```markdown
# Knowledge Gap Report — 2026-05-13

## High priority (guests asked, no answer found)
- "Is there a kayak?" — asked twice, unanswered
- "Where's the nearest pharmacy?" — asked once, unanswered

## Missing topic areas
- Emergency contacts (GP, A&E, plumber, electrician)
- Bad weather / indoor activities
- Checkout procedure and key return
- Laundry facilities

## Thin sections (exist but could be expanded)
- Local restaurants — only 2 listed, no descriptions or opening hours
- Parking — no mention of overflow parking for larger groups
```

## 9. Docker & QNAP deployment

### 9.1 `Dockerfile`

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
```

### 9.2 `docker-compose.yml`

Two services: the Node app, and a Caddy reverse proxy that provides SSL via Let's Encrypt.

```yaml
services:
  chatomatic:
    build: .
    restart: always
    ports:
      - "127.0.0.1:3000:3000"      # LAN-only direct access; Caddy fronts the public URL
    volumes:
      - /share/Public/chatomatic/data:/app/data
    env_file:
      - .env
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3000/health"]
      interval: 30s
      timeout: 5s
      retries: 3

  caddy:
    image: caddy:2-alpine
    restart: always
    ports:
      - "80:80"
      - "8443:8443"                # 8443 (not 443) because QTS itself holds 443
    volumes:
      - /share/Public/chatomatic/Caddyfile:/etc/caddy/Caddyfile:ro
      - /share/Public/chatomatic/caddy_data:/data
      - /share/Public/chatomatic/caddy_config:/config
    depends_on:
      - chatomatic
```

Adjust `/share/Public/chatomatic/` to match your NAS folder structure if different.

### 9.3 `.env.example`

```env
ANTHROPIC_API_KEY=sk-ant-...
GMAIL_USER=you@gmail.com
GMAIL_APP_PASSWORD=xxxx-xxxx-xxxx-xxxx
DIGEST_EMAIL=you@gmail.com
DIGEST_CRON=0 7 * * *
HOUSE_NAME=Honeysuckle Cottage
RATE_LIMIT_MAX=30
PORT=3000
```

Copy to `.env` and fill in values. **Never commit `.env` to git.**

### 9.4 QNAP setup steps

**Caddyfile** at the project root provides SSL via Let's Encrypt with no QNAP-specific reverse proxy. (Newer QTS builds no longer ship Application Portal; even when present it adds complexity Caddy avoids.)

```caddy
{
    http_port 80
    https_port 8443
}

your-host.myqnapcloud.com {
    reverse_proxy chatomatic:3000
    encode gzip
}
```

Setup steps:

1. **Container Station** — install it from App Center if missing
2. **Place project on NAS** — clone or copy to `/share/Public/chatomatic/` (or your preferred path; update volume paths in `docker-compose.yml` to match)
3. **Volumes** — `mkdir -p data caddy_data caddy_config` inside the project folder; place `knowledge.md` inside `data/`
4. **`.env`** — copy from `.env.example` and fill in real values
5. **QNAP DDNS** — Control Panel → myQNAPcloud or Network & File Services → DDNS — choose a hostname; verify it resolves to your public IP
6. **Edit `Caddyfile`** — replace `your-host.myqnapcloud.com` with your actual DDNS hostname
7. **Router port forwards** — external 80 → NAS-LAN-IP:80, external 443 → NAS-LAN-IP:8443 (both TCP). Most consumer routers under NAT Forwarding / Virtual Servers / Port Forwarding.
8. **Bring it up** — `cd /share/Public/chatomatic && docker compose up -d --build`
9. **Watch Caddy log** for cert issuance — `docker logs -f chatomatic-caddy-1` — look for `certificate obtained successfully`
10. **Gmail App Password** — Google Account → Security → 2-Step Verification → App Passwords → generate one for "Chatomatic"; put it in `.env` as `GMAIL_APP_PASSWORD`

**Port choice rationale:** QTS binds host port 443 (`fcgi-pm` web server) and 8080 (admin UI), so Caddy can't reuse them. Port 80 on the NAS is typically free. The router does NAT translation (external 443 → NAS 8443) so the public URL stays clean — no port suffix.

**If the LE cert challenge fails:** Either ISP is blocking port 80 inbound, or the router rule isn't applied. Caddy will fall back to TLS-ALPN-01 on port 443/8443 automatically — so as long as one of the two paths is reachable, the cert issues. Future renewals also work via either.

### 9.5 Updating the knowledge base

```bash
# On the NAS, edit the file directly:
# /share/homes/admin/chatomatic/data/knowledge.md

# Then restart the container in Container Station, or via SSH:
docker compose restart chatomatic
```

No image rebuild is required. The `data/` directory is a volume — changes to `knowledge.md` are picked up on restart.

## 12. Out of scope (explicitly)

These were considered and rejected during design:

- **Admin UI** — owner edits `knowledge.md` directly; no browser-based editor needed
- **User login / accounts** — public access + rate limiting is sufficient for a trusted circle
- **RAG / vector search** — prompt caching with full doc achieves equivalent accuracy at this scale
- **Streaming responses** — structured JSON output (answer + suggestions) is incompatible with streaming; Haiku is fast enough that latency is not a concern
- **Public question feed** — question log is owner-private only
- **Cross-session memory** — conversation context is in-session only; no persistent user state
